# Design

## Context

See `proposal.md` for motivation. Relevant current-state facts that shape the approach:

- `writeScannerState`/`writeMapState` (`src/lib/state-manager.js`) currently `messageDelete` then `imap.append`. `readScannerState` currently takes `results[0]` from an IMAP `SEARCH`, which returns UIDs in ascending order — i.e. today it reads the *oldest* match, not the newest.
- Folder paths flow from `src/lib/utils/config.js` (raw, `.`-joined strings) into `src/lib/clients/imap-client.js`'s `open`, `search`, `moveMessage(s)`, `appendMessage`, and into `state-manager.js` directly via `imap.mailboxOpen`/`imap.append`. Only `createAppFolders` (used solely by `init-workflow.js`) already translates the delimiter, via `collectFoldersToCreate` in `src/lib/utils/mailboxes-utils.js`.
- `processWithRspamd` (`src/lib/services/message-service.js`) and `trainSpam`/`trainHam` (`src/lib/services/training-service.js`) both use `Promise.all(...)` over a `map` whose inner `try/catch` just rethrows — so one rejection aborts the whole `Promise.all`. `checkEmail`/`learnHam`/`learnSpam` (`src/lib/clients/rspamd-client.js`) throw plain `Error` objects with no structured status; `parseRspamdOutput` (`src/lib/utils/email-parser.js`) throws a plain `Error` on unexpected shape.
- The orchestrator (`src/orchestrator.js`) opens a new IMAP connection per step (see `orchestration` spec's "Step connection isolation") and runs `runInit` exactly once at startup, before any training or scan step, in the same process. This means folder resolution only needs to happen once per process, and every later step's workflow code, even on its own IMAP connection, needs some way to see the resolved values without re-resolving or needing an `imap` handle.

## Goals / Non-Goals

**Goals:**
- Make the three underlying finding fixes (3.1, 4.2, 4.4) each internally coherent (e.g. 3.1's write-ordering fix requires the read-side max-UID fix to not be silently defeated by a crash mid-write).
- Keep the folder-resolution and error-classification mechanisms small, single-purpose modules that existing workflows import, not a broader config/architecture rewrite.
- Fix the three failing tests (4.8) and bring README/`.env.example` (4.11, 4.12) in line with `config.js`'s actual defaults.

**Non-Goals:**
- IMAP `NAMESPACE` handling (server-required/forbidden `INBOX.` prefixing) — the review flags this as part of 4.2's full recommendation, but the concrete, verifiable bug is the delimiter mismatch; namespace handling has no failing case in this codebase today and would need a namespace-aware test server to validate. Left as a follow-up.
- Finding 5.5's other sub-issues (dead code after the `if (!json)` check, `originalPath` restore not in a `finally`, substring `HEADER` search) — only the max-UID selection is pulled in, because 3.1 depends on it. The rest of 5.5 is untouched.
- A "failed" training folder or any new folder for un-learnable messages — permanently-failing training messages are left in place (and logged at `warn` every cycle they recur), per the review's simpler documented alternative. Not moved anywhere new.
- Finding 5.10 (config schema / generated docs) — `.env.example` and README are hand-aligned to `config.js` for this change, not schema-generated.
- Admin scripts under `src/admin/` and `src/read-email.js`-style debug scripts — these already default `FOLDER_INBOX` to `"INBOX"` (a single path segment, so delimiter translation is a no-op today) and are not part of the review's cited "Where" for 4.2. Not wired into folder resolution.

## Decisions

**3.1 — Append-then-delete, keyed delete, max-UID read.**
`writeScannerState`/`writeMapState`: capture the old matching UID(s) via `search` *before* appending (as today), but reorder to `imap.append(...)` first, then `imap.messageDelete` scoped to the old UID(s) captured before the append (not a fresh `search` after — a fresh post-append search would also match the just-appended message). `readScannerState`/(map read path, if any exists today — currently there is none, map state is write-only per the review; not adding one) select `Math.max(...results)` instead of `results[0]`.
*Alternative considered*: delete-then-append with a pre-write backup copy. Rejected — strictly more IMAP round-trips for the same guarantee the review's own recommended ordering already gives for free.

**3.1 — Default state `UIDNEXT - 1` requires opening the target mailbox first.**
`readScannerState` is called before the caller has opened the mailbox it's about to scan (see `scan-workflow.js`'s `runScan`, which calls `readScannerState` before `open(imap, FOLDER_INBOX)`). To compute `UIDNEXT`, `readScannerState` needs a `mailboxPath` argument (the caller's target mailbox) so it can peek that mailbox's status independently of the state-folder mailbox it opens for the state search itself (via `imap.status(mailboxPath, {uidNext: true})`, which does not require the mailbox to be selected). This is a signature change: `readScannerState(imap, defaultState)` becomes `readScannerState(imap, defaultState, mailboxPath)`. `map-workflow.js`'s map-state reads (if they use the same default-state path) are unaffected since maps don't have a "mailbox UIDNEXT" concept — only the scanner-state caller passes `mailboxPath`.

**4.2 — Mutate `config.FOLDER_*` in place; no separate accessor (revised from an earlier `getFolder(key)`/cache design).**
`src/lib/utils/folder-resolver.js` exports a single function, `resolveFolders(imap)` (called once, during `runInit`): it gets the server delimiter, then loops `Object.keys(config)` and for every key starting with `FOLDER_` whose value is a `string`, replaces `config[key]` with its delimiter-translated form via the shared `splitFolderParts(path)` helper (extracted from `collectFoldersToCreate` in `mailboxes-utils.js`, so there's exactly one definition of "what characters count as a path separator"). Every call site keeps reading `config.FOLDER_*` exactly as it always has, for this setting and every other one — one access pattern everywhere, no `getFolder('FOLDER_X')`/`getFolders()` indirection layer, no parallel list of folder keys to keep in sync with `config.js`. The `typeof value === 'string'` guard means a future non-path `FOLDER_*` setting (e.g. a boolean flag) is silently skipped rather than crashing the resolver. `createAppFolders` (`imap-client.js`) is left as-is — it already does its own correct delimiter translation for hierarchy creation, and feeding it already-resolved paths is harmless (idempotent re-split/rejoin using the same real delimiter).
*Alternative considered (originally implemented, then revised on user feedback)*: a `getFolder(key)` accessor backed by a module-level resolved-map cache, keyed by a hand-maintained `FOLDER_KEYS` array. Rejected after implementation — every call site used a different access pattern (`getFolder('FOLDER_X')`) than the rest of `config`'s settings (`config.SETTING`), including a file (`folder-processor.js`) that used *both* patterns for the same key in the same function; and `FOLDER_KEYS` was a second, easy-to-forget place to add a new folder setting alongside `config.js` itself. Mutating `config` in place removes both problems at once.
*Alternative considered*: resolve lazily on first use per-connection. Rejected — every step opens a fresh connection (per `orchestration`'s "Step connection isolation"), so lazy-per-connection resolution would mean an extra `LIST` call on every single step instead of once per process run, for no benefit (the delimiter cannot change mid-run).
*Trade-off accepted*: mutating shared config state means a workflow that (hypothetically) read a folder setting before `resolveFolders()` ran would silently get the raw, un-resolved value instead of a loud "not resolved yet" error (which the rejected `getFolder()` design provided). This is judged acceptable because the `orchestration` spec's "One-time init phase" requirement already guarantees `runInit` — and therefore `resolveFolders` — runs before any training or scan step in every real code path; there is no runtime guard against a future out-of-order call, only this structural guarantee.

**4.4 — Status/marker properties on errors, not string matching.**
`rspamd-client.js`'s `checkEmail`/`learnHam`/`learnSpam` attach `err.status = response.status` when the failure came from a non-OK HTTP response. `email-parser.js`'s `parseRspamdOutput` attaches `err.permanent = true` when the response shape is invalid. New `src/lib/utils/error-classifier.js` exports `isPermanentError(err)`: true if `err.permanent === true`, or if `err.status` is in `[400, 500)`; false (transient) otherwise, including for plain network/`fetch` errors that carry neither property — this fail-safe default preserves today's "unknown failure fails the batch for retry" behavior for anything not explicitly recognized as permanent.
*Alternative considered*: regex/string matching on `err.message`. Rejected — brittle against message wording changes, and the two thrown-error sites already have the real information (`response.status`, "this parse failed") available to attach directly.

**4.4 — `Promise.allSettled` + explicit per-message try/catch, batch-level rethrow for transient.**
`processWithRspamd` and `trainSpam`/`trainHam` switch their `Promise.all(messages.map(...))` to `Promise.allSettled(...)`. Each mapped async function still has an inner `try/catch`: on a **permanent** error it logs at `warn` and resolves with a `null`/skip marker (never rejects); on a **transient** error it rethrows (so that message's promise is `rejected` in the settled results). After `allSettled`, the caller collects transient rejections; if any exist, it throws a single aggregate error (batch fails, whole batch retried by the orchestrator's existing retry path — unchanged from today) — but only after already having logged and skipped every permanent failure, so a permanent failure never contaminates a transient-failure retry.
`scan-workflow.js`'s `last_uid` calculation already uses the full fetched `messages` array (not `processedMessages`), so a permanently-skipped message's UID is naturally included when the batch's `last_uid` is computed and written — no separate "advance past skipped" logic is needed.
`train-workflow.js`'s `runTraining` moves only the messages the training call reports as learned; permanently-failing ones stay in the training folder (see Non-Goals) and are picked up again — and re-logged at `warn` — on the next training cycle.

**4.12 — `SPAM_PROCESSING_MODE` and `AI_MODEL`: code defaults changed, not just docs (user decision during implementation).**
Task 7.6 flagged that `.env.example`'s `SPAM_PROCESSING_MODE=folder` and `AI_MODEL=gpt-5-nano` disagreed with `config.js`'s fallback defaults (`label`, `gpt-4o-mini`) and asked the user which side was correct. The user's answers went beyond "align the docs" and specified the actual desired runtime behavior:
- `SPAM_PROCESSING_MODE`'s code default is changed to `'folder'` (was `'label'`) - `folder` is more broadly visible across mail clients (see review finding 5.22 - many clients don't surface IMAP keywords) and is what `.env.example` already recommended.
- `AI_MODEL` no longer has a default (was `'gpt-4o-mini'`, now `''` if unset). `config.js`'s load-time IIFE now throws a clear error when `AI_ENABLED=true` and `AI_MODEL` is unset/empty, so a misconfiguration fails fast at process startup instead of failing per-message inside `classifyWithAi`. This is a small, targeted piece of finding 5.10 (config validation) pulled into this change because it was the direct, simplest way to honor the user's answer, not a broader validation-schema effort.
This makes `.env.example`'s existing `SPAM_PROCESSING_MODE=folder` and `AI_MODEL=gpt-5-nano` correct as-is (no value change needed there) — only their explanatory comments needed updating to describe the new reality (no more "differs from the code default" caveat for `SPAM_PROCESSING_MODE`; `AI_MODEL`'s comment now says "required when AI_ENABLED=true, no default" instead of implying a fallback exists).

**3.1 follow-up — `SCAN_INITIAL_STATE` (user request after implementation).**
3.1's own fix (initializing `last_uid` to `UIDNEXT - 1` instead of `0` when no state exists) is deliberately safe-by-default: it protects a first run against an unwanted full-inbox scan/AI-classification bill. But the user pointed out this makes "actually scan everything from the beginning" — a real, frequently-wanted case (auditing an existing inbox, backfilling training data) — impossible without manually forging a state message. Added a new `SCAN_INITIAL_STATE` config setting (`new` default, or `all`) read inside `readScannerState`'s existing no-state branch: `all` skips the `UIDNEXT` peek entirely and uses the caller-supplied default `last_uid` (`0`) unconditionally, regardless of mailbox contents. Validated at `config.js` load time against a fixed `['new', 'all']` allow-list (fail fast on a typo, same pattern as `AI_MODEL`'s required-when-enabled check), rather than silently falling back to `new` on garbage input.
*Alternative considered*: a one-shot CLI/admin flag or a `--rescan-all` argument to `orchestrator.js` instead of a persistent env setting. Rejected — the existing admin scripts (`src/admin/`) already manipulate state directly (e.g. deleting the state message to force a rescan), which is the existing supported way to do a one-off reset; `SCAN_INITIAL_STATE` addresses the narrower, config-shaped case of "what should happen automatically the first time this deployment ever runs," which fits naturally alongside the other `SCAN_*` settings.
*Scope note*: this setting only governs the *no-state* default; it has no effect once a scanner state message exists (matching how `defaultState`/`mailboxPath` already behave in `readScannerState` today).

## Risks / Trade-offs

- **[Risk]** A message that keeps failing with a 4xx forever (e.g., a genuinely malformed `.eml` a user drops in a training folder) will be re-logged at `warn` every single cycle indefinitely, since it's left in place rather than moved or marked. → **Mitigation**: acceptable per the review's own "leave them and log once" fallback option; a `scanner.train.failed` folder or once-only logging is left as a clearly-scoped follow-up (see Non-Goals) rather than adding new folder-creation/init surface to this change.
- **[Risk]** `readScannerState`'s new `mailboxPath` parameter changes its call signature; any other caller (tests, other workflows) must be updated together with `scan-workflow.js`. → **Mitigation**: `grep` for all `readScannerState` call sites during implementation (task list includes this explicitly) and make the parameter required only where a scanner-state default is requested, matching the two current real callers.
- **[Risk]** Classifying an HTTP 4xx as always "permanent for this message" could be wrong for a rare rate-limit-as-4xx response from rspamd (unlikely — rspamd doesn't use 429, and there's no evidence of it in this codebase). → **Mitigation**: none needed today; flagged here so a future rspamd behavior change is easy to trace back to this decision.
- **[Risk]** Attaching `.status`/`.permanent` to thrown `Error` objects is a small, easy-to-miss contract between `rspamd-client.js`/`email-parser.js` and the new `error-classifier.js`. → **Mitigation**: covered by unit tests asserting the properties are set at the throw sites, and by `isPermanentError` unit tests covering both properties plus the "neither present" fail-safe-transient default.

## Migration Plan

No data migration. Rollout is a single deploy of the updated container image; no `.env`/schema changes are required (folder *values* in `.env.example` are corrected to match existing `config.js` defaults — see 4.12 — not changed in meaning). Rollback is a plain image revert; the state-write and folder-resolution changes are backward-compatible with state/messages written by the previous version (same message format, same folder names once resolved).
