# Proposal

## Why

The 2026-09-17 codebase review (`docs/review/20260917-codebase-review.md`) identified six findings that together threaten the scanner's core promise — "scan every message exactly once, don't lose track, don't get stuck" — and undermine first-run trust in the docs: a state-write bug that can trigger a full-inbox rescan (3.1, Critical), a hard-coded folder delimiter that silently breaks the app on `/`-delimited IMAP servers (4.2), a single malformed message that can halt scanning/training forever and crash-loop the container (4.4), a red test suite hiding real regressions (4.8), and a README/`.env.example` that actively contradict the code's real defaults and behavior (4.11, 4.12). These are bundled into one change because they were reviewed and prioritized together and several touch the same code paths (state-manager, workflows, config/docs).

## What Changes

- **State write durability (3.1)**: `writeScannerState`/`writeMapState` append the new state message before deleting older ones (was delete-then-append), so a failed append never leaves the state folder empty. `readScannerState` selects the highest-UID state message (was the first/lowest result) so it reads the newest state even if a crash leaves more than one message behind — this selection fix is required for the append-then-delete ordering to be meaningful. When no state message exists, the scanner initializes `last_uid` according to a new `SCAN_INITIAL_STATE` setting: `new` (default) starts at `UIDNEXT - 1` if the inbox is non-empty (scan only new mail, preserving the original 3.1 fix); `all` always starts at `0` so the first scan covers the entire existing inbox. Either way it logs a `warn`. This knob was added on direct user request after implementation, since a full-inbox scan on first run is a real, frequently-wanted use case that the original 3.1 fix otherwise made impossible.
- **Folder delimiter resolution (4.2)**: configured folder paths (`FOLDER_INBOX`, `FOLDER_SPAM`, `FOLDER_SPAM_LOW/HIGH`, `FOLDER_TRAIN_*`, `FOLDER_STATE`) are resolved once at startup against the IMAP server's actual hierarchy delimiter (discovered via `LIST`), and every workflow that opens, searches, moves, or appends to a folder uses the resolved path instead of the raw `.`-joined config string. Fixes the app being unusable on `/`-delimited servers (Gmail, Outlook/Exchange, many Dovecot setups, Fastmail).
- **Per-message failure isolation (4.4)**: scanning (`processWithRspamd`) and training (`trainSpam`/`trainHam`) no longer abort an entire batch when one message fails. Each message's outcome is classified as transient (network error, 5xx, timeout, no HTTP status — retry the whole batch, current behavior) or permanent-for-this-message (4xx, response parse failure — skip that message, log at `warn`, let the rest of the batch and the state/move-forward proceed). This stops a single "poison" message from halting scanning/training indefinitely and crash-looping the container via `MAX_RETRIES`.
- **Test suite fixed (4.8)**: the three tests in `test/email-parser.test.js` and `test/rspamd-maps.test.js` that assert stale behavior (pre-`isWhitelisted` add-header semantics; pre-insertion-order map sorting) are updated to match current, intentional behavior. No production code changes result from this item alone.
- **README and defaults alignment (4.11, 4.12)**: `README.md` is corrected against the current code for every discrepancy in the review's 4.11.a–4.11.q table (scores, folder name defaults, state-storage claims, script locations, batch size default, missing settings, legacy/placeholder content, `docker compose` v2 CLI, the Gmail-labels claim). `.env.example` and README-documented defaults are aligned to `src/lib/utils/config.js`'s actual runtime defaults for every row in the review's 4.12 table (`FOLDER_STATE`, `FOLDER_TRAIN_*`, `SCAN_INTERVAL`, `SCAN_BATCH_SIZE`, `SPAM_PROCESSING_MODE`, `AI_MODEL`, `IMAP_TLS`). `config.js` is treated as the single source of truth by direct alignment; a generated/shared config schema (finding 5.10) is explicitly out of scope.

## Capabilities

### New Capabilities
- `state-manager`: durability and read/write ordering guarantees for the mailbox-stored scanner/map state (append-before-delete, newest-state selection, non-zero default initialization).
- `folder-resolution`: translation of configured, delimiter-neutral folder paths into the IMAP server's real hierarchy paths, resolved once at startup and used consistently by all folder operations.
- `batch-processing-resilience`: per-message fault isolation during scan and training batch processing, with transient-vs-permanent error classification.

### Modified Capabilities
_None._ `scan-inbox`'s and `orchestration`'s existing requirements are unaffected by this change — the new capabilities above add requirements alongside them without altering their contracts (`scan-inbox`'s UID filtering and `orchestration`'s step-retry/exit behavior on an unhandled step error both still apply; this change reduces how often a step *throws* in the first place, it doesn't change what happens when one does).

## Impact

- **Modified files**: `src/lib/state-manager.js`, `src/lib/utils/config.js` (new `SCAN_INITIAL_STATE` setting, default `new`, validated at load time; `SPAM_PROCESSING_MODE` and `AI_MODEL` default/validation changes made during implementation per user decision — see `design.md`), `src/lib/utils/mailboxes-utils.js`, `src/lib/clients/imap-client.js`, `src/lib/workflows/scan-workflow.js`, `src/lib/workflows/train-workflow.js`, `src/lib/workflows/map-workflow.js`, `src/lib/workflows/init-workflow.js`, `src/lib/workflows/idle-workflow.js`, `src/lib/services/message-service.js`, `src/lib/services/training-service.js`, `src/lib/clients/rspamd-client.js`, `src/lib/utils/email-parser.js`, `test/email-parser.test.js`, `test/rspamd-maps.test.js`, `README.md`, `.env.example`.
- **New files**: `src/lib/utils/folder-resolver.js` (or similarly named module) for delimiter-aware folder path resolution; `src/lib/utils/error-classifier.js` (or similar) for transient/permanent error classification shared by scanning and training.
- **No changes** to `docker-compose.yml`, rspamd config, or any security/exposure findings (3.2, 4.1, 4.7, 4.13, 4.14) — those are separate findings not in scope here.
- **No new dependencies.**
