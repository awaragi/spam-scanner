- [x] 2.1 Create `runtime/mailbox-runner.ts` with the `JobName` union (`'scan' | 'trainSpam' | 'trainHam' | 'trainWhitelist' | 'trainBlacklist'`) and the `JobState` interface from design.md D1; verify the file compiles with `nest build`.
- [x] 2.2 Implement `MailboxRunner`'s constructor taking the mailbox, its job dependencies (`FolderInitService`, `RspamdTrainingService`, `SenderListTrainingService`, `ScanService`), config, and a logger, porting `openSession`/session-per-job unchanged from `runtime/mailbox-loop.service.ts` per design.md D4; verify with a unit test that a job's `fn` receives a `MailboxSession` built the same way (session opened, folders resolved, session closed via `safeLogout` in `finally` even when `fn` throws).
- [x] 2.3 Implement the `runJob` single-flight-with-coalescing wrapper exactly as design.md D2 (status guard, `dirty` flag, `do/while`); verify with unit tests: (a) a second call while `status === 'running'` does not start a concurrent run and instead sets `dirty`, (b) three triggers arriving during one run produce exactly one extra run afterward, not three and not zero, (c) `this.stopped` set mid-coalesce stops the `do/while` from re-running.
- [x] 2.4 Implement `attempt()` and `backoffMs()` exactly as design.md D3, including the mailbox-level derived `degraded`/`lastError`; verify with unit tests: (a) `attempt()` skips `fn` entirely and returns without calling it when `Date.now() < nextEligibleAt`, (b) three consecutive failures produce a strictly increasing `nextEligibleAt` delay each capped at 30 minutes, (c) a success after failures resets `consecutiveFailures` to 0 and `nextEligibleAt` to 0, (d) a connect failure inside `fn` (thrown before the job body runs) is recorded as an ordinary job failure, per D4.
- [x] 2.5 Implement `MailboxRunner.triggerNow(job: JobName)` per design.md D8 (reset `consecutiveFailures`/`nextEligibleAt` to 0, then call `runJob` immediately, bypassing the backoff check); verify with a unit test that calling `triggerNow` while a job is within its backoff window runs immediately anyway, and that a subsequent success leaves `consecutiveFailures` at 0.
- [x] 2.6 Implement `MailboxRunner.getStatus(): MailboxRunnerStatus` per design.md D5 (ISO timestamps, `state` derived from any job having `consecutiveFailures > 0`, `mode` read from the field D6/task 3 will set); verify with a unit test asserting the exact shape for a runner with one job mid-backoff (state `'degraded'`, that job's `consecutiveFailures` and `nextEligibleAt` populated, other jobs untouched).
- [x] 2.7 Implement `MailboxRunner.stop()` setting the stopped flag checked by `runJob`'s `do/while` and by the job-trigger call sites (interval tick, IDLE loop) added in task 3, per design.md D9; verify with a unit test that `stop()` called mid-coalesce prevents the pending extra run.

## 3. IDLE-first triggering and the global interval (D6, D7)

- [x] 3.1 Add a `start()` method to `MailboxRunner` that opens the mailbox's first connection, runs folder init once (porting `bootstrapMailbox`'s success/failure handling from `mailbox-loop.service.ts` unchanged), and on success checks `imap.capabilities.has('IDLE')` on that same connection before closing it, recording the result as `mode: 'idle' | 'loop'` for the runner's lifetime per design.md D6; verify with unit tests using a fake `ImapFlow` whose `capabilities` map does/doesn't have `'IDLE'`, asserting `getStatus().mode` matches.
- [x] 3.2 Implement the global interval inside `MailboxRunner.start()`: on every `ScanConfig.scanIntervalSeconds` tick, call `runJob('trainSpam', ...)`, `runJob('trainHam', ...)`, `runJob('trainWhitelist', ...)`, `runJob('trainBlacklist', ...)`, and `runJob('scan', ...)` only when `mode === 'loop'` (per D7); verify with a unit test using a fake timer that a `'loop'`-mode runner's tick calls all five jobs, while an `'idle'`-mode runner's tick calls only the four training jobs.
- [x] 3.3 For `mode === 'idle'`, open a second dedicated connection (`disableAutoIdle: true` per the Context section) and run a loop calling `infrastructure/imap/inbox.watcher.ts`'s `waitForNewMail`, calling `runJob('scan', ...)` on each resolution and immediately re-arming; verify with a unit test (fake `waitForNewMail` resolving twice then aborted via `stop()`) that `scan` is triggered once per resolution and the loop exits cleanly on `stop()`.
- [x] 3.4 Add reconnect-with-backoff for a dropped/errored IDLE connection, reusing `backoffMs()` from task 2.4, without changing `mode` back to `'loop'` (per D6's explicit "does not change mode back to loop"); verify with a unit test that a thrown/rejected `waitForNewMail` call is followed by a retry after a backoff delay, with `mode` still `'idle'` throughout.
- [x] 3.5 Confirm the safety-net requirement end-to-end at the unit level: an `'idle'`-mode runner whose IDLE connection never resolves still gets a `scan` job run when the interval fires, per the `mailbox-runtime` spec's "The interval triggers a scan even while IDLE is active" scenario.
