# Design

## Context

`front/` is an Angular 22 standalone-component app (no NgModules) with four pages (`login`, `admin`, `mailbox`, `sender-list-panel`) and a thin `ApiService`/`auth-storage` pair. There is currently no component library and almost no CSS - see proposal.md "Why" for the resulting UX problems this change fixes.

Two sessions exist today, distinguished by what `auth-storage.ts` holds: an admin session (`adminToken` in `localStorage`) and a mailbox session (`mailboxToken` + `mailboxId` in `sessionStorage`, obtained by exchanging the admin token - `AdminComponent.openMailbox()`). `mailboxGuard` currently requires *both* an admin token and a matching mailbox session to reach `/mailbox/:id`; there is no independent mailbox-owner login today. This change does not touch that - it only makes the existing admin-vs-mailbox route distinction visible in the nav.

Server-side data this design relies on, confirmed by reading `server/src/`:
- `GET /mailboxes/:id/status` already returns `MailboxRunnerStatus`, which (when enabled) includes `jobs: Record<JobName, {status: 'idle'|'running', ...}>` for the five coalesced jobs (`scan`, `trainSpam`, `trainHam`, `trainWhitelist`, `trainBlacklist`). `init-folders` is not one of these five (`job-name.ts`) and has no tracked running state.
- `GET/PUT /mailboxes/:id/settings` already reads/writes `MailboxSettings` (folders, `scanRead`, `scanInitialState`, `processingMode`, `labels`, `thresholds`, `aiEscalation`, `aiEnabled`) - a form just didn't exist on top of it.
- `GET/PUT/DELETE /mailboxes/:id/state` already reads/writes/deletes a `ScannerState` (`last_uid`, `last_seen_date`, `last_checked`, `uid_validity?`) - small enough to summarize directly, no new endpoint needed.

So every behavior in the proposal (per-job disable, settings form, state summary+reset) is achievable with existing endpoints; this is purely a front-end design.

## Goals / Non-Goals

**Goals:**
- Pick concrete Angular Material modules, a theming approach, and a small set of genuinely shared pieces (not per-page duplicates) for feedback, confirmation, and status display.
- Decide where role-aware nav logic lives and how "job running" is read without new server state.
- Decide the shared/reusable component boundary precisely enough to write tasks against.

**Non-Goals:**
- No dark-mode toggle or multi-theme support - Material's theme will use one fixed palette. (Material 3's CSS custom properties make a dark-mode follow-up cheap later, but it isn't asked for now.)
- No E2E/browser test suite - existing component-level testing conventions apply (see tasks.md).
- No per-field override granularity (D12) - a UI section's override is all-or-nothing, even though the server's stored overrides can be field-granular within a group.

**Revised**: "no new or changed server endpoints" (the original Non-Goal here) turned out not to hold - D12 needed one, to tell a stored override apart from a value that merely equals its default. Everything else about this change stayed presentation-layer only.

## Decisions

### D1: Angular Material, M3 theming, no animations package
Add `@angular/material` and `@angular/cdk` as dependencies (via `ng add @angular/material`, whose Angular 22 schematic only asks for a starter palette - it no longer has a typography or animations prompt at all). Use Material's M3 system-level theming (`@use '@angular/material' as mat;` + `mat.theme(...)`, emitted by the schematic as `src/material-theme.scss` and wired into `angular.json`'s `styles` array ahead of `styles.css`) rather than the legacy pre-built theme files.

Originally planned to also register `provideAnimationsAsync()` - **revised after running the schematic**: `@angular/material@22` no longer peer-depends on `@angular/animations`, that package isn't installed anywhere in the repo, and `provideAnimationsAsync()`/`provideAnimations()` are deprecated (slated for removal in v23) in favor of the native `animate.enter`/`animate.leave` template syntax. Material's own `ng add` schematic does not wire either provider for Angular 22. So: no animations provider is added. Material components render and function without one (Angular's renderer no-ops the animation-engine hooks they call); if a later change wants enter/leave transitions, that's the native `animate.enter`/`animate.leave` syntax, not the deprecated providers - out of scope here.

Each standalone component imports only the specific Material modules it uses (`MatButtonModule`, `MatTableModule`, etc.) - consistent with the existing no-NgModule style, no shared "MaterialModule" barrel (that pattern re-imports unused modules into every consumer and is exactly the kind of catch-all abstraction the project avoids).

### D2: Only build shared components that are used 3+ times identically; everything else stays per-page
The proposal sketched "status badge, confirm-dialog, data table, action group, empty state" as illustrative. Looking at actual reuse across the four pages:
- **Confirm dialog**: reused for delete-account and reset-state (and possibly disable-mailbox later) → build it, as a `ConfirmDialogComponent` (`MatDialog` content) plus a tiny `ConfirmDialogService.confirm({title, message}): Observable<boolean>` wrapper so call sites don't repeat `MatDialog.open()` boilerplate.
- **Feedback**: every single action across every page needs success/failure reporting → build a `NotifyService` wrapping `MatSnackBar.open()` with two helpers (`success(message)`, `error(message)`) and consistent duration/`panelClass`. This directly replaces the `output.set(JSON.stringify(...))` pattern repeated in every component today.
- **Status badge**: the same enabled/running/degraded vocabulary appears on the admin mailbox list and the mailbox detail header → build a small `StatusBadgeComponent` (`@Input` status, renders a colored `mat-chip` or equivalent).
- **Data table**: rejected as a shared abstraction. There is one table on the admin page (see D11) and no second table anywhere else; a generic wrapper would add an indirection layer to save nothing. It uses `mat-table` directly.
- **"Action group" / "empty state"**: rejected as standalone components for the same reason - each page's empty/action state is small enough to write inline with Material primitives (`mat-card`, `@if`) without a wrapper.

This narrows the shared library to three pieces: `ConfirmDialogComponent`/`ConfirmDialogService`, `NotifyService`, `StatusBadgeComponent`, under `front/src/app/shared/`.

**Revised during implementation:** every page's error handler needs to turn an `HttpErrorResponse` into the message passed to `NotifyService.error(...)` - the same `err.error?.message ?? err.message ?? fallback` extraction the old `output.set(JSON.stringify(err.error ?? err.message))` calls already did inline, repeated at every one of the ~20 call sites being touched. Pulled out as a fourth shared piece, `http-error.util.ts`'s `httpErrorMessage(err, fallback?)` - a pure function, tested directly rather than through a component.

### D3: Role-aware nav lives in the shell component, computed from the current URL - no new session service
A new `AppShellComponent` wraps `<router-outlet>` with a `<mat-toolbar>`. It derives `isAdminRoute = url.startsWith('/admin')` from `toSignal(router.events...)` (filtered to `NavigationEnd`) and renders admin-nav vs. mailbox-nav content accordingly, reading `getMailboxId()` from `auth-storage` for the mailbox-nav label. A dedicated session/role service was considered and rejected: the only state involved is "which route prefix am I on," which is one computed signal: introducing a service for it would be indirection with no second consumer.

### D4: Per-job disable reads the existing `/status` response; no polling changes
`MailboxComponent` already calls `refreshStatus()` after every mutating action. Add a signal holding the latest `jobs` record from that response, and compute each job-trigger button's `disabled` state as `jobs[jobName]?.status === 'running'`. `init-folders` has no entry in `jobs` (see Context) - its trigger is left always-enabled; the server's own coalescing in `triggerInitFolders` still prevents concurrent runs, so this is a display gap, not a correctness gap. No new polling/interval is introduced - the existing refresh-after-action flow is sufficient per the "disabled while running" scenarios in specs/front-end/control-ui/spec.md.

**Corrected during implementation:** `MailboxController.triggerJob` `await`s `RunnerRegistry.triggerNow` to completion before responding - so a job the UI itself just triggered is already back to `idle` by the time the trigger's own response (and the status refresh that follows it) arrives. There is no "optimistic disable then reconcile" window for a self-triggered job. The disabled state only becomes observable for a job already running from another source when the page's `jobs` signal is refreshed (e.g. the mailbox's own IDLE/interval loop, or another open tab) - still correctly handled by the same binding, just not exercisable by clicking a trigger and watching it disable itself.

### D5: Settings become a reactive form grouped to match `MailboxSettings`'s own structure
One `MailboxSettingsComponent` (or a section within the mailbox page) with Material form fields grouped as: Folders (8 text fields), Scanning behavior (`scanRead` toggle, `scanInitialState` radio/select), Processing mode (`processingMode` select + conditional label fields), Thresholds (3 numeric fields), AI escalation (2 numeric fields). Submits the whole form via the existing `PUT .../settings`. No partial-save affordance - matches the existing all-or-nothing update endpoint.

**Corrected during implementation:** `aiEnabled` is NOT part of this form. Reading `settings-update.schema.ts` (`PUT .../settings`'s request schema) shows it `.refine()`s to outright reject any body containing `aiEnabled` with a 400 - that flag is admin-only, set through the account API (`PATCH /admin/accounts/:id`, already wired in task 5's accounts table). Submitting the settings form with an `aiEnabled` field would 400 on every save.

**Reworked per user feedback - see D12**: this original design submitted the *whole* form, every group, every time. The first real use of the shipped form (task 6.4's own verification) silently wrote a full override for a mailbox that had never had one - exactly the bug D12 exists to fix.

### D6: Scanner state becomes a read-only summary + a confirmed reset action
`last_uid`, `last_seen_date`, `last_checked`, `uid_validity` are rendered as labeled fields (a `mat-list` or simple definition list) when present, or an explicit "no state yet" empty message when `GET state` returns `null`. The existing `DELETE state` call becomes a "Reset state" button gated by `ConfirmDialogService`.

### D7: Sender-list panel keeps the bulk-paste textarea, restyled; no chip preview
The textarea editor plus import/export is genuinely useful (bulk paste/replace, file import/export) and isn't raw JSON output - it's the list's own natural text format. Only the status/error messaging (`message` signal holding `JSON.stringify(err...)`) is replaced, with `NotifyService`.

**Revised twice during implementation**: first added an at-a-glance `mat-chip-set` preview above the editor (proposal.md's "Material list with chips"), capped and filtering blank entries (a stored list can contain blanks a write would reject - see `sender-list.util.ts`'s now-removed `previewAddresses`). Then removed entirely per user feedback - the chip preview added visual noise without enough value over the count header + textarea already showing the same information. The count header (`{{ addresses().length }} address(es)`) stays as the only at-a-glance summary.

### D8: Create-account and mailbox-settings each become their own route
Two new routes, both reachable only through the existing guards (no new auth concept):
- `admin/accounts/new` → a new `CreateAccountComponent`, `canActivate: [adminGuard]`. Replaces the inline "Create account" card on `AdminComponent`, which instead gets a single "Add account" button that `routerLink`s there. On success, navigates back to `/admin`.
- `mailbox/:id/settings` → `MailboxSettingsPanelComponent` itself, `canActivate: [mailboxGuard]`. Rather than wrapping it in a thin page component, `MailboxSettingsPanelComponent` is changed to read `mailboxId` the same way `MailboxComponent` already does (`route.snapshot.paramMap.get('id') ?? getMailboxId()`) instead of taking it as an `@Input` - it's no longer embedded in `MailboxComponent`'s template, so the `@Input` had no remaining purpose. `MailboxComponent` gets a "Settings" button that `routerLink`s there, and the settings page gets its own "Back to mailbox" link (the shell toolbar's "Back to admin" goes to `/admin`, not back to the mailbox detail page, so this route needs its own way back).
- `nav-role.util.ts` needs no change: both new paths still match `startsWith('/admin')` / `startsWith('/mailbox/')`.

### D9: A new account's mailbox id is derived from the IMAP username when possible; a conditional email field covers the rest
`accountRecordSchema.id` is `z.email()` - always a valid email, described in its own doc comment as "the mailbox owner's email address... distinct from `imapUser`, which may be a bare username on some providers." The create-account form drops the separate "Mailbox id" field; the primary field is "IMAP username" (plain text, not `type="email"`, since a bare username is valid IMAP input).

**Revised after user feedback** (the initial version made the username field `type="email"` and required, which silently dropped the bare-username case the schema's own doc comment calls out): the username field is now watched reactively (`isEmailShaped()`, a small shared pure-function predicate in `shared/email.util.ts` - deliberately loose, since it only decides which field supplies the id, not whether the id is ultimately valid; the server's `z.email()` stays the real validator). While the username looks like an email, it's submitted as both `imapUser` and `id`, and no second field is shown. The moment it doesn't, a conditional "Email" field appears (`@if (!usernameIsEmail())`) and supplies `id` instead, while the username field still supplies `imapUser` verbatim. The post-delete prefill (D-level convenience, not a spec requirement) follows the same rule, using the deleted account's `imapUser` as the username field and only populating the conditional email field when that `imapUser` isn't email-shaped.

### D10: Responsive layout via container scrolling + flex-wrap, no breakpoint-specific component variants
No separate mobile layouts or component variants. Three mechanical changes cover it:
- Both `mat-table`s (`admin.component.ts`) get wrapped in a `.table-scroll { overflow-x: auto }` container, so a cramped table scrolls horizontally within its own box instead of blowing out the page width - the standard pattern for a data table that can't meaningfully reflow into a single column without becoming a different component.
- Flex containers that weren't already wrapping (`mat-card-actions` in the sender-list panel, the shell toolbar's nav content) get `flex-wrap: wrap`; everything else (`job-row`, `checkbox-row`, every form) was already a wrapping flex row or a single column.
- The shell's `main` padding drops from `1.5rem` to `1rem` under a `max-width: 599px` media query (Material's own phone breakpoint), so phone-width content isn't fighting fixed padding on both sides for the same screen space.
No JS-driven responsive logic (no `BreakpointObserver`) - everything here is static CSS, since nothing changes behavior at a breakpoint, only layout.

### D11: Admin shows one merged mailbox/account table, not two
The admin page originally showed two separate tables - "Mailboxes" (from `GET /admin/mailboxes`, live runner status) and "Accounts" (from `GET /admin/accounts`, persisted config) - both listing the same ids, with two separately-wired "Enabled" toggles that called the exact same `PUT /admin/mailboxes/:id/enabled` endpoint. User feedback: this reads as two different things to an admin, when it's one mailbox with a persisted config and a live status. Merged into a single table, keyed by id: a `rows` computed signal joins `accounts()` (the row's base fields - host, port, `aiEnabled`) with `mailboxes()` (overlaid `state`/`mode`/`lastError` for the status badge), so there is one row, one "Enabled" toggle, one "AI" toggle, one Open/Delete action group per mailbox. The two underlying API calls stay separate (they're still two different server resources), merged client-side only - no server change.

### D12: An "Override defaults" checkbox per settings section, backed by a new `overriddenKeys` field on `GET .../settings`
**The bug**: `GET .../settings` has only ever returned *resolved* settings - defaults merged with any stored override, with no way to tell which is which. D5's original form patched every field from that resolved response and submitted the whole thing on every save, which means simply opening the settings page and clicking Save - with nothing edited - silently turned every default into a pinned, permanent override. A mailbox that had never been configured would, after one open-and-save, never again pick up a future code-default change.

**The fix has two parts, server and front:**
- **Server** (new, minimal): `MailboxRunner` already computes `validateOverrides(rawOverrides, ...)` at bootstrap and discards the result, keeping only the fully-resolved `MailboxSettings`. It now also keeps the validated overrides object itself (`private overrides: OverridableSettings`), exposed as `getOverriddenKeys(): string[]` (`Object.keys(this.overrides)`). `RunnerRegistry.getMailboxSettingsView(mailboxId)` reads both `getSettings()` and `getOverriddenKeys()` from the *same* runner instance in one call (so a concurrent settings-triggered restart can never make them describe two different bootstraps), replacing the old `getMailboxSettings`. `GET .../settings`'s response shape changes from bare `MailboxSettings` to `{ settings: MailboxSettings; overriddenKeys: string[] }` - the only caller was this controller route, so this is a clean shape change, not a breaking change to some other consumer.
- **Front**: `mailbox-settings.util.ts` defines the 5 UI sections (`SETTINGS_SECTIONS`) and maps them to the schema's top-level keys (a section can span more than one key - "Scanning behavior" covers both `scanRead` and `scanInitialState`). Each section gets an "Override defaults" `mat-checkbox`, initialized from `sectionsWithOverride(overriddenKeys)` on load. Checked → that section's form controls are `.enable()`d (editable); unchecked → `.disable()`d (read-only, showing the current resolved value - which, since it's not overridden, *is* the default, by construction - no separate "fetch the defaults" call needed). On save, `buildSettingsOverrideBody()` explicitly includes only the overridden sections' keys; an empty result (nothing checked) submits `{}`, which - given `writeSettingsOverrides` always replaces the whole stored overrides message - correctly reverts every setting to its default in one save.

**Found via live testing, not assumption**: the first implementation submitted `this.form.value` directly, trusting Angular's reactive-forms doc that a disabled `FormGroup`'s value is excluded from its parent's `.value`. Direct inspection of the running component (`ng.getComponent(el)`) showed `form.value` included every key regardless of disabled state - contradicts the documented behavior, cause not fully root-caused (nonNullable FormBuilder interaction? version-specific?), not worth chasing further. Fixed by not depending on that behavior at all: `buildSettingsOverrideBody()` takes `form.getRawValue()` (always includes everything, disabled or not) and filters explicitly by the `overridden` set, which is this component's own source of truth anyway.

### D13: A 401 from any API call forces a clean logout, not just the route guards' presence check
`adminGuard`/`mailboxGuard` only check that a token *exists* in storage at navigation time - they say nothing about whether it's still valid. A token can expire (1h TTL, see `API_ADMIN_TOKEN_TTL`/`API_MAILBOX_TOKEN_TTL`) while the user is sitting on an already-loaded page with no navigation of their own, and every subsequent API call then 401s - the various `NotifyService.error(...)` call sites show a generic failure toast (or, for silent background calls, nothing at all), but nothing takes the user back to `/login`.

Fixed with a functional `HttpInterceptorFn` (`auth.interceptor.ts`, registered via `provideHttpClient(withInterceptors([authInterceptor]))`), not a change to the guards - the guards still correctly gate *navigation*, this handles a session dying *during* a page's lifetime. On any 401 except `/auth/login`'s own (wrong password - the login page's existing inline error, not a session-expiry signal - `isSessionExpiredResponse()`, a pure predicate so the admin/login carve-out is unit-tested directly), it clears both token stores, shows `NotifyService.error('Your session has expired. Please log in again.')`, navigates to `/login`, and swallows the error (`EMPTY`) rather than rethrowing - otherwise the originating call site's own error handler would also fire, showing a second, redundant toast right as the page navigates away.

The server confirmed (investigated, not assumed, before implementing): every invalid-token case - missing, malformed, expired, wrong-scope - surfaces as a plain `401 Unauthorized` from `verifyBearerToken` (`server/src/api/common/guards/token.util.ts`), with no custom exception filter changing that shape, and no refresh mechanism exists (expiry always means re-login, for both admin and mailbox tokens). A single status-code check is sufficient; no response-body parsing needed to distinguish cases.

### D14: Job triggers show in-flight feedback and refresh scanner state, not just runner status
User feedback: clicking Scan showed nothing changing. Two real gaps, not a misunderstanding of the badge (the "Running" status badge reflects the runner's health - `jobs`/`degraded` - not whether a job is currently executing, and correctly staying "Running" the whole time is right):
1. **No in-flight indicator.** `MailboxController.triggerJob` awaits the job to completion before responding (D4) - the POST itself takes as long as the job, and nothing showed that it was in progress. Fixed with a `pendingJobs` signal: a job's own button disables and shows a small spinner for the duration of its request, set in `triggerJob()` before the call and cleared in both the success and error paths.
2. **Scanner state never refreshed after a job.** `triggerJob()`'s success handler only called `refreshStatus()`, never `reloadState()` - so `last_uid`/`last_seen_date`/`last_checked` stayed stale after a scan that plainly changed them. Fixed by calling both on success.

**Verified, including a legitimate "nothing changed" case**: triggering Scan against a real mailbox showed the spinner, a "scan finished." snackbar, and a `GET .../status` + `GET .../state` round-trip (confirmed via network request log) - but `last_checked` itself didn't move. Traced to `PendingMessagesStep.locate()` (`server/src/application/scanning/pending-messages.step.ts`): when there's no new mail and no UIDVALIDITY change, it returns early without writing scanner state at all - deliberate, documented server behavior, not a bug. The front-end fix is correct regardless: it reflects whatever the server actually did, every time, instead of only updating runner status.

## Risks / Trade-offs

- [Risk] `init-folders` can't show a "running" disabled state (D4) → Mitigation: documented as a known, accepted gap; server-side coalescing already makes it safe to leave clickable.
- [Risk] M3's `mat.theme()` Sass API differs from older Material versions readers may expect → Mitigation: pin to the Angular Material version matching `@angular/core`'s `^22.2.0`, which only ships the M3 API; no fallback path needed.
- [Risk] Replacing `output.set(JSON.stringify(...))` everywhere touches every component's error-handling call sites → Mitigation: `NotifyService` has a two-method surface (`success`/`error`), making each call site a one-line swap; tasks.md sequences this page-by-page, not as one sweeping change.
- [Risk] D9's `isEmailShaped()` is a loose heuristic (not full email validation) deciding which field supplies the id → Mitigation: it only ever widens to show the extra field, never silently drops data - a false "looks like an email" still gets rejected by the server's real `z.email()` validator on submit, surfaced as an ordinary error via `NotifyService`.
